# Data schema

Source of truth: `apps/api/prisma/schema.prisma`. Postgres 16, accessed through Prisma. Every foreign key has a matching index on the owning table, every lookup column used in a `WHERE` is indexed, and every id is a UUID generated by the database driver (`@default(uuid())`), never a sequential integer, so ids don't leak row counts or creation order.

## Entity map

```
User ──┬── Class (teacherId)
       ├── Enrollment ── Class (many students ↔ many classes)
       ├── Quiz (ownerId)
       ├── PracticeSession (studentId)
       ├── Attempt (studentId)
       ├── Mastery (studentId, per topic)
       ├── RefreshToken / PasswordResetToken
       ├── AssignmentTarget (studentId)
       └── AiCall (userId)

Topic ──┬── Question
        ├── Quiz
        ├── Mastery
        └── PracticeSession

Quiz ── QuizQuestion ── Question   (ordered, many-to-many)
Quiz ── Assignment ── Class        (a quiz handed to a class, with a due date)
Assignment ── AssignmentTarget ── User   (per-student completion row)

PracticeSession ── Attempt (one session has many attempts)
Question ── Attempt

AuditLog   — standalone, hash-chained, never updated or deleted
```

## Tables

### `users`
One row per account (student, teacher or admin — `Role` enum). `passwordHash` is Argon2id, never the plaintext. `disabled` is checked on every authenticated request, not just at login, so disabling someone takes effect immediately. Indexed on `role` because the admin user list filters by it.

### `refresh_tokens`
Backs session renewal (`SEC-2`). Each row is one refresh token, stored only as a SHA-256 `tokenHash` (the raw token never touches the DB). Rows carry a `familyId`: every token issued from the same login chain shares one family, so if a `revokedAt` token is ever presented again — meaning it was stolen and the thief raced the real user — the whole family is revoked and the session dies instead of silently trusting the replay. Indexed on `userId` and `familyId`.

### `password_reset_tokens`
One single-use, 30-minute, hashed token per reset request (`FR-4`). `usedAt` is set the moment it's redeemed so the same link can't be replayed.

### `classes`
A teacher's roster. `joinCode` is unique and is what students type in to enrol (`FR-10`). `archived` hides a class without deleting its history.

### `enrollments`
The many-to-many join between `classes` and `users` (students). Composite primary key `(classId, studentId)` — a student can't join the same class twice. Indexed on `studentId` for "my classes" lookups.

### `topics`
The subject taxonomy (e.g. "Linear equations", "Fractions"), each tagged with a `gradeLevel`. Everything adaptive (questions, mastery, sessions, quizzes) hangs off a topic.

### `questions`
The question bank. `difficulty` is 1–5, `type` is `multiple_choice` or `numeric`, `options` is JSON (null for numeric), and `correctAnswer`/`explanation` are never sent to the student until after they answer. `status` (`draft` → `approved` → `retired`) is the content lifecycle — only `approved` questions are ever served in practice (`FR-30..32`). `source` (`human`/`ai`) tracks provenance for the Week 3 AI-generated content. Composite index on `(topicId, difficulty, status)` because that's exactly the filter the adaptive picker uses on every question served.

### `quizzes`
A teacher-curated or assigned set, scoped to one `topic`. `status` is `draft` until published.

### `quiz_questions`
Join table giving a quiz's questions a fixed order (`position`). Composite primary key `(quizId, questionId)` plus a unique `(quizId, position)` so two questions can't occupy the same slot.

### `assignments`
A quiz handed to a class with a `dueAt`. `wholeClass` means every current *and future* member of the class gets it, not just who was enrolled at assignment time.

### `assignment_targets`
One row per student the assignment actually applies to. This exists so "has this student finished?" is a single indexed lookup (`completedAt IS NULL`) rather than a join and count — whether a row exists at all is also how a class-wide assignment gets expanded per-student (a row is created lazily the first time that student is relevant).

### `practice_sessions`
The resumable state machine behind one practice run (`FR-11`, `FR-16`). Holds `currentDifficulty` and `streak` (adaptive engine state), `currentQuestionId` (the one question currently in flight — set once, cleared on answer, so a page refresh or a second tab reopens the exact same question instead of skipping it), and running `answeredCount`/`correctCount`. `assignmentId` is null for free topic practice; when set, the session serves a fixed quiz instead of adapting difficulty. Indexed on `(studentId, completedAt)` for "my open sessions" and on `assignmentId`.

### `attempts`
An immutable log: one row per answer submitted, with the `difficulty` the question was actually served at (so this doesn't drift if the question's own difficulty is edited later), `timeMs`, and whether it was `correct`. This is the raw material both the adaptive engine (to avoid repeating a question in-session) and the progress dashboards (accuracy, streaks, trend) read from. Indexed on `(studentId, createdAt)`, `sessionId`, and `questionId`.

### `mastery`
One row per `(student, topic)` — the current skill estimate (`score`, an EWMA between 0 and 1) and a running `attempts` count. Composite primary key `(studentId, topicId)` means the "get my mastery in this topic" read and the per-answer write are both a single-row upsert, not a scan.

### `audit_logs`
Append-only and hash-chained (`SEC-14`): each row's `hash` is computed over its own fields plus the previous row's `hash` (`prevHash`), and a DB trigger rejects any `UPDATE` or `DELETE` on the table outright — so even a compromised app server can't quietly rewrite history, only an admin with direct DB access attempting it would have the chain visibly break at a verify check. `actorId` is intentionally **not** a foreign key: deleting a user must never require rewriting (or cascading into) audit history. Indexed on `actorId`, `action`, and `createdAt` for the audit viewer's filters.

### `ai_calls`
Metering for the Week 3 AI features: provider, model, token counts, cost and latency per call. Deliberately metadata-only — no prompt or response text, let alone student answers, is stored here (`AI-24`), so this table carries no PII risk even though it's queried for cost dashboards.

## Design notes

- **Indexing rule:** every column a route filters or sorts by has a matching index — this was a deliberate pass, not incidental (see the scalability notes in `CLAUDE.md` for the few spots, like `AuditLog` listing and random question pick, that still use `OFFSET` paging or a full-table scan and would need to change before the data size grows past a few hundred thousand rows).
- **Soft lifecycle over hard delete:** `disabled` (users), `archived` (classes), `retired` (questions) — rows are never deleted out from under a foreign key that other rows (attempts, audit entries, enrollments) still need to reference.
- **Hashing, never storage, of secrets:** refresh tokens and password-reset tokens are stored as `sha256`/argon2 hashes only; the raw value exists only in the cookie/email sent to the user.
